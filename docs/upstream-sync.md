# Upstream sync

Rook is a fork of [warpdotdev/Warp](https://github.com/warpdotdev/warp). This file records how far it has been brought forward, so `/catch-up` knows where to start.

**Last synced upstream commit:** `51242b5f0af80fff81613ff6561eed29ba8922fa` (2026-09-07, "[REV-2383] Scope model listing to selected team (#15804)")

## Where Rook deliberately differs

Taking an upstream change on top of one of these would silently undo it. Check before porting anything that touches them.

| Area | Rook's position | Where |
| --- | --- | --- |
| GPU selection on Windows | Defaults to the discrete GPU. Upstream prefers the integrated one, which renders the terminal on the iGPU of any machine with a dedicated card. Crash recovery falls back to integrated rather than out of it. | `app/src/settings/gpu.rs`, `app/src/crash_recovery.rs` |
| `blocks` table | Indexed on `(pane_leaf_uuid, is_background)`, and blocks belonging to closed panes are deleted at startup. Upstream has no index and no cleanup, so the retention count after every command scans the whole table. | `crates/persistence/migrations/2026-09-07-120000_index_blocks_and_command_history`, `app/src/persistence/block_list.rs` |
| Session persistence | Written every 15 seconds and again on termination. Upstream only writes on window move, resize, focus change and close, so a shutdown loses whatever changed since the last of those. | `app/src/persistence/mod.rs`, `app/src/lib.rs` |
| Server endpoints | Point at `.invalid` hosts, not a server. The rename turned upstream's own `warp.dev` into `rook.dev`, which is registered to somebody else and resolves, so `RookServerConfig`, `OzConfig` and the install-detection server's CORS allowlist used it for the server, RTC, session-sharing and Oz endpoints, and the default git-agent-commit email used it too. `.invalid` is reserved by RFC 2606 so it can never resolve; unreachable rather than empty, because some call sites parse the URL and expect the parse to succeed. The Firebase auth key is empty instead, since it is a query parameter rather than a host. | `crates/rook_core/src/channel/config.rs`, `crates/rook_core/src/channel/state.rs`, `crates/app-installation-detection/src/lib.rs`, `app/src/ai/agent_sdk/driver/git_credentials.rs` |
| Update checking | Asks the GitHub releases API and reports a newer version; it does not download one. Upstream's version server refuses the `oss` channel outright, so its pipeline could never have served this fork. `ContextFlag::PromptForVersionUpdates` also reports disabled whenever the `Autoupdate` feature is, which upstream keeps independent - taking their `context_flag.rs` restores a "Check for updates" button and a `workspace:check_for_updates` binding whose requests are dropped before they are sent. `is_current_version_ahead_of_latest_version` falls back to `github::compare_release_tags` when `ParsedVersion` cannot read a tag, because its regex only accepts the dated `v0.YYYY.MM.DD.HH.MM.channel_NN` shape and every semver tag that merely differed from the installed one was treated as newer; releases carry the dated shape now, so the fallback is only for installs still on a `v0.1.x` tag. Finding an update is also not an error here: upstream's `UnableToUpdateToNewVersion` means "you are not allowed to install this" and is drawn in red, while on this fork it is the ordinary outcome, so the banner and the two menu entries say a version is available and offer to open the release page. The "more info" link behind the failure went to `docs.rook.dev`, which the rename invented and somebody else owns. | `app/src/autoupdate/github.rs`, `app/src/autoupdate/mod.rs`, `app/src/workspace/view.rs`, `crates/rook_core/src/context_flag.rs` |
| Release versioning | Tags are `v0.YYYY.MM.DD.HH.MM.oss_NN`, cut by `script/release_tag`. This is upstream's own scheme, which the tree was already built for and this fork spent three releases not using: `ParsedVersion` parses nothing else and `script/update_plist` derives the numeric `CFBundleVersion` from those fields. A date also says more than a semver number would, there being no published API here to promise compatibility about. | `script/release_tag`, `CLAUDE.md` |
| Block retention | A pane drops its oldest blocks past `terminal.max_retained_output_lines`. Upstream evicts nothing, so a pane grows for as long as it is open. | `app/src/terminal/model/blocks.rs`, `app/src/terminal/settings.rs` |
| Finished-block storage | Compacted into flat storage on finish, above a five-row threshold that upstream does not have. Upstream gates the compaction on `MaximizeFlatStorage`, which only their feature-flag server can turn on, so in a fork it never runs at all. | `app/Cargo.toml`, `app/src/features.rs`, `crates/rook_terminal/src/model/grid/grid_handler.rs` |
| CLI-agent plugins | Vendored under `plugins/`, one process per hook. Rook installs these and refuses the upstream builds, which still carry the per-tool-call cost. | `plugins/` |
| Working-directory chip | Clicking it opens the directory in the file manager when it has no menu to show. Upstream leaves that branch of the chip with no click handler at all, which is what it renders while a CLI agent session is running - so for anyone running an agent in the terminal the path is inert. | `app/src/context_chips/display_chip.rs` |
| Reveal in the file manager | A "Reveal in Explorer" entry on the working-directory bar's context menu and on the block menu, both dispatching `ContextMenuAction::RevealWorkingDirectory`. Upstream offers neither, and reaches the file manager only from the code editor and its file tree. The platform-specific label those two call sites spelled inline is now `util::file::reveal_in_file_manager_label`, so porting either of them back re-inlines it and the menus drift apart. | `app/src/terminal/view.rs`, `app/src/util/file.rs`, `app/src/code/view.rs`, `app/src/code/file_tree/view.rs` |
| Pane rename shortcut | F2 renames the focused pane. Upstream ships both rename actions with no default binding, and in the pane list its F2 would do nothing at all: the tab it renames has no visible name there to edit. | `app/src/util/bindings.rs`, `app/src/workspace/mod.rs` |
| Per-directory pane names | A pane is named by its working directory through `appearance.panes.default_names_by_path`, matched on the longest directory prefix, so a name set on a repository root covers everything inside it. Upstream has nothing like it. Resolved where the name is drawn rather than stored on the pane, so it follows a `cd` and picks up an edit to the setting on the next frame. A name the user types still wins and does not write back to the setting - which is the point: one directory can have a default name and a second pane in it be called something else. | `app/src/settings/pane.rs`, `app/src/pane_group/mod.rs`, `app/src/workspace/view/vertical_tabs.rs` |
| Community link | Discord, not the upstream Slack workspace. | `app/src/util/links.rs` |
| Secret-redaction tests | `secrets_tests.rs` takes a mutex and restores the previous patterns on drop, because every test in it writes the process-wide `SECRETS_REGEX`. Upstream has no such guard; without it the tests pass or fail depending on how the harness schedules them. | `crates/rook_terminal/src/model/grid/secrets_tests.rs` |
| CI and release | Rewritten for this fork. CI runs clippy, tests and a release-profile check on Windows, macOS and Linux, plus `cargo fmt --check` on Linux alone, since formatting is platform independent. A `v*` tag builds three installers - Windows `.exe`, macOS `.dmg`, Linux AppImage - and attaches them to the GitHub release. Upstream's pipelines drive their own infrastructure and cannot run here. Tests run with `--no-fail-fast`, because the default hides every failure behind the first. The triggers carry no `paths-ignore`: a filtered-out workflow creates no checks at all, so a required check would wait forever on a documentation-only change. The `changes` job holds the filter instead and the jobs skip their steps. | `.github/workflows/` |
| Shell-dependent tests | Eight tests are excluded on Linux and macOS and kept on Windows. They spawn a real zsh, bash or fish and read back its options or its executables, which a hosted runner does not reliably provide - macOS installs no test shells at all, and even with zsh installed the spawned session returns no options. Upstream runs them on its own infrastructure, where that works. Excluded by name, so a new failure cannot hide inside the rule; all eight predate this fork's first commit. | `.github/workflows/ci.yml` |
| Launching at login | Off unless asked for. Upstream defaults `general.login_item` on, so the app writes itself into the user's Run key on first launch without being asked, and a machine that boots into a terminal nobody opened is the result. The toggle in Settings -> Features still registers it, and leaving it off unregisters what an earlier build added. | `app/src/terminal/general_settings.rs`, `app/src/login_item/windows.rs` |
| Installer display name | The Windows installer shows `Rook` while the app keeps identifying itself as `RookOss`. Upstream uses one name for both, which puts the channel suffix in the Start menu, in Add/Remove Programs and in Windows Search. The identity half cannot follow: it is the AppUserModelID, the URL scheme and the per-user data directories, and renaming it orphans an existing install's data. Publisher and support URL are the fork's too - upstream's named their company and a domain this project does not own. | `script/windows/bundle.ps1`, `script/windows/windows-installer.iss`, `script/windows/tui-installer.iss` |
| First-frame work | Runs on every launch. Upstream registers the first-frame callback only for logged-in users, because the startup telemetry event was its only consumer - so in a build with no server to log in to, the GPU state and the graphics-backend dropdown were never refreshed and the startup timings were computed nowhere. The timings are now logged, which is the only way a build without telemetry can see where its startup went; only the telemetry send is still conditional. | `app/src/lib.rs`, `crates/rook_core/src/interval_timer.rs` |

## What the rename must not touch

`script/rebrand.py` carries the current list and the reasoning. In short: repositories under the upstream organisation other than the client itself, the five external crates whose package names carry the upstream brand, and the protobuf types and fields reached through `api::`. Each of those lives in another repository, so renaming it here only breaks the build.

There is one exception of a different kind: `warp pointer`, in `crates/computer_use/src/linux/x11/`. That is the English word - X11's `XWarpPointer` teleports the cursor and predates the terminal by decades - so the name is local code, not a foreign identifier, and it is a collision the "belongs to another repository" rule would never flag. Renaming it broke the Linux build, which nothing checked from Windows.

Those are names the rename must leave alone. There is a second failure mode it cannot prevent, because nothing in the renamed text is wrong: **assertions that depend on a literal it did change.** Four tests broke this way, and all four compiled cleanly.

- `regex_right`, `regex_left` and `nested_regex` search for `Wa.*123` and `Wa.*rp` in fixtures that said `Warp`. The needles are fragments, not the whole word, so they stayed put while the haystack became `Rook` and the searches began returning `None`.
- `test_find_url_omits_trailing_periods` hard-codes the columns a URL occupies. `github.com/warpdotdev/Warp` became `github.com/FJRG2007/rook` and lost two characters; the column numbers did not move.
- `deserialize_mixed_environment_uses_per_repo_forges` is the inverse: its fixture's `"repo": "warp"` was renamed to `"rook"`, while the clone URL it asserts, `https://github.com/warpdotdev/warp.git`, was *deliberately preserved* by the rule that protects the upstream repository. The protection and the rename disagreed, and the test compared one against the other.

After re-running the rename, run the tests on every platform rather than only building. A fragment of the brand used as a search pattern, and a hard-coded length or offset into a renamed literal, are the two shapes to look for.
